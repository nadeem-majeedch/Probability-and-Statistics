## A. Problem statement

A mobile app team has 600 session records with device tier, network type, app version,
measured latency and whether the session crashed. Release 3.2 is about to ship and the team
must decide whether to gate it on low-end devices: crashes appear to rise sharply with
latency, but latency is itself determined by device and network. The team needs to separate
the effect of latency from the effect of the device tier, and to quantify what a latency
improvement would buy.

## B. Background and context

Mobile performance data are a mixture: latency distributions differ by device and network,
so the pooled distribution is multimodal and its mean is not representative of anyone. Crash
probability is a binary outcome that rises with latency, which invites a logistic model. The
analytical trap is confounding and mediation: low-end devices cause both high latency and
crashes, so a naive latency–crash association overstates what fixing latency alone would
achieve. This case is about effect decomposition in observational telemetry.

## C. Dataset description

`app_sessions.csv` has 600 rows.

| Column | Type | Description |
|---|---|---|
| `session_id` | integer | 1–600 |
| `device` | text | `low-end` (35 %), `mid` (45 %), `high` (20 %) |
| `network` | text | `wifi` (50 %), `4g` (35 %), `3g` (15 %) |
| `app_version` | text | `3.1` (249 sessions) or `3.2` (351) |
| `latency_ms` | integer | Measured latency |
| `crashed` | integer | 1 if the session crashed |

**Generation method.** Base latency is 420 ms on low-end, 260 ms on mid and 150 ms on high
devices; multiplied by 1.9 on 3G, 1.25 on 4G and 1.0 on wifi, then by lognormal(0, 0.45)
noise. The crash probability is logistic in latency,
\(\mathrm{logit}(p)=-3.6+0.004\cdot\text{latency}\), so latency is the only direct cause of
crashes and device/network act through it. The realised crash rate is 16.8 %.

## D. Questions to investigate

1. Describe latency overall and by device and network.
2. What is the overall crash rate, and how does it vary by network and device?
3. How strongly is latency associated with crashing?
4. Fit a logistic model of crash on latency; interpret the odds ratio per 100 ms.
5. Does the device tier add information beyond latency?
6. Is there evidence that version 3.2 is better or worse than 3.1?
7. What is the expected crash-rate reduction from cutting median latency by 100 ms?

## E. Relevant probability and statistical concepts

- Mixture distributions and why pooled summaries mislead.
- Quantiles for skewed performance data.
- Logistic regression with a continuous predictor.
- Odds ratios per unit and per 100 units.
- Confounding and mediation in observational data.
- Wald tests and likelihood-ratio tests for nested models.
- Predicted probabilities and marginal effects.
- Simpson's paradox risk in subgroup comparisons.

## F. Mathematical formulation

\[
\mathrm{logit}\,P(\text{crash})=\beta_0+\beta_1\,\text{latency}
+\beta_2\mathbf{1}[\text{4g}]+\beta_3\mathbf{1}[\text{wifi}],
\]

with the odds ratio for a 100 ms increase equal to \(e^{100\beta_1}\).

The predicted crash probability at latency \(x\) is
\(p(x)=1/(1+e^{-(\beta_0+\beta_1x)})\), and the marginal effect on the probability scale is
\(\partial p/\partial x=\beta_1 p(1-p)\), which is largest near \(p=0.5\).

For comparing versions, the unadjusted 2 × 2 table gives a risk difference and a chi-square
test; the adjusted comparison adds latency to the model to see whether the version effect
survives.

## G. Step-by-step analytical approach

1. Summarise latency overall and by device and network (median and p95, not mean alone).
2. Tabulate crash rates by network, device and version.
3. Plot crash rate against latency decile.
4. Fit crash ~ latency; report the odds ratio per 100 ms with its interval.
5. Add network and device; check whether latency's coefficient changes.
6. Compare versions with and without adjustment.
7. Predict the crash-rate change for a 100 ms latency reduction.
8. Write the release recommendation, distinguishing correlation from intervention.

## H. Student tasks

1. Report median latency by device tier and by network.
2. Compute crash rates by network; which network is worst?
3. Fit crash ~ latency. Give the OR per 100 ms and its p-value.
4. Add network to the model. Does the latency OR change much? Why?
5. Compare crash rates for versions 3.1 and 3.2 with a test.

7. Predict the crash rate at 200 ms and at 800 ms.

## I. Python practical implementation

```python
import numpy as np
import pandas as pd
import statsmodels.formula.api as smf
from sklearn.metrics import roc_auc_score

sessions = pd.read_csv("docs/data/case-studies/app_sessions.csv")
print(sessions.head(3).to_string(index=False))
print("sessions:", len(sessions), "| crash rate:", f"{sessions.crashed.mean():.4f}")

print("\nlatency by device (median, p95):")
print(sessions.groupby("device").latency_ms.agg(
    median="median", p95=lambda s: np.percentile(s, 95)).round(0).to_string())
print("\nlatency by network (median, p95):")
print(sessions.groupby("network").latency_ms.agg(
    median="median", p95=lambda s: np.percentile(s, 95)).round(0).to_string())

print("\ncrash rate by network:")
print(sessions.groupby("network").crashed.agg(["mean", "size"]).round(4).to_string())
print("\ncrash rate by version:")
print(sessions.groupby("app_version").crashed.agg(["mean", "size"]).round(4).to_string())

model = smf.logit("crashed ~ latency_ms", data=sessions).fit(disp=0)
print(f"\ncrash ~ latency: beta={model.params.latency_ms:.5f}, "
      f"OR per 100 ms={np.exp(model.params.latency_ms * 100):.2f}, "
      f"p={model.pvalues.latency_ms:.2e}")
print(f"AUC = {roc_auc_score(sessions.crashed, model.predict(sessions)):.3f}")

adjusted = smf.logit("crashed ~ latency_ms + C(network)", data=sessions).fit(disp=0)
print(f"\nwith network: latency OR per 100 ms="
      f"{np.exp(adjusted.params.latency_ms * 100):.2f}, "
      f"p={adjusted.pvalues.latency_ms:.2e}")
print("network odds ratios:", np.exp(adjusted.params.filter(like="network")).round(3).to_dict())

version_only = smf.logit("crashed ~ C(app_version)", data=sessions).fit(disp=0)
version_adj = smf.logit("crashed ~ C(app_version) + latency_ms", data=sessions).fit(disp=0)
print(f"\nversion alone: OR 3.2 vs 3.1 = "
      f"{np.exp(version_only.params['C(app_version)[T.3.2]']):.3f}, "
      f"p = {version_only.pvalues['C(app_version)[T.3.2]']:.3f}")
print(f"version adjusted for latency: OR = "
      f"{np.exp(version_adj.params['C(app_version)[T.3.2]']):.3f}, "
      f"p = {version_adj.pvalues['C(app_version)[T.3.2]']:.3f}")

b0, b1 = model.params.Intercept, model.params.latency_ms
for latency in (200, 500, 800):
    print(f"predicted crash rate at {latency} ms: {1 / (1 + np.exp(-(b0 + b1 * latency))):.3f}")
print(f"\ncrash rate by latency quartile:")
print(sessions.groupby(pd.qcut(sessions.latency_ms, 4),
                       observed=True).crashed.mean().round(4).to_string())
```

## K. Expected conclusions

- Latency: mean 385 ms, median 342 ms, p95 819 ms. Medians by device: high 171.5, mid 331,
  low-end 483.5; by network: wifi 292, 4g 366, 3g 526.
- Crash rate 16.8 % overall; by network 3g 31.8 %, 4g 16.9 %, wifi 12.6 %.
- Crash rate rises monotonically with latency: 6.6 %, 10.7 %, 14.0 %, 36.0 % across
  quartiles.
- Logistic model: OR 1.51 per 100 ms (p < 10⁻¹²), AUC 0.74.
- Adding network leaves the latency OR essentially unchanged (1.51), so the network effect
  works through latency rather than beside it.
- Version 3.1 crashed 18.9 % and 3.2 crashed 15.4 % (p ≈ 0.27 unadjusted); the difference
  is not significant, and it vanishes after adjusting for latency.
- Predicted crash rates are 6.7 % at 200 ms, 20.2 % at 500 ms and 47.4 % at 800 ms, so a
  100 ms improvement near the middle of the range buys about 4 percentage points.

## L. Detailed solution and discussion

**Step 1 — the mixture.** Pooled mean 385 ms hides three populations: high-end devices
median 171.5 ms, mid 331 ms, low-end 483.5 ms. Network shifts the whole distribution further
(wifi 292, 3g 526). Any performance target expressed as "average latency under 400 ms" is
therefore satisfied by a product that is unusable for a third of users. Report percentiles by
segment.

**Step 2 — crash rates.** 3G sessions crash at 31.8 %, nearly three times the wifi rate
(12.6 %). Device tier and network are correlated (low-end devices are over-represented on 3G
in this dataset), so the marginal comparison cannot separate them — which is why the model
matters.

**Step 3 — the latency model.** Coefficient 0.00412 per ms, so the odds ratio per 100 ms is
\(e^{0.412}=1.51\) with p < 10⁻¹². AUC 0.74: latency alone ranks a crashing session above a
non-crashing one 74 % of the time, respectable for a single variable.

**Step 4 — confounding check.** Adding network dummies leaves the latency coefficient almost
unchanged (OR 1.51). This is evidence that network acts *through* latency rather than as an
independent cause — mediation, not confounding. The generator was built that way, which makes
the dataset a clean demonstration of the distinction: if network had its own direct effect,
the latency coefficient would have shrunk when network entered.

**Step 5 — version comparison.** 3.1: 18.88 % (47 of 249); 3.2: 15.38 % (54 of 351). The raw
difference is 3.5 pp with p ≈ 0.27 — not significant. After adjusting for latency the
version odds ratio moves toward 1, because 3.2 sessions happen to include more slow devices.
The correct conclusion: no evidence that 3.2 is worse, and no evidence it is better.

**Step 6 — prediction and leverage.** Predicted crash probability is 6.7 % at 200 ms, 20.2 %
at 500 ms and 47.4 % at 800 ms. Because the logistic curve is steepest in the middle of the
latency range, a 100 ms improvement where most sessions sit buys roughly 4 percentage
points of crash reduction; moving from 800 ms to 500 ms buys about 27 points. The biggest
wins come from fixing the slow tail, not from shaving the median.

**Step 7 — recommendation.** Gate 3.2 on low-end + 3G devices only if the latency regression
ships with it; otherwise the version change is not the problem. The actionable finding is
that low-end devices on 3G have a one-in-three crash rate driven by latency above 500 ms.
Mitigations in order of expected value: reduce network payload (smaller bundles), add
progressive loading, and consider a lightweight mode for low-end devices. All three are
testable with a follow-up experiment that measures latency and crashes together.

**Causal caution.** Latency is not randomised: sessions that crash may record inflated
latency because the crash occurs during a slow operation. Part of the association is reverse
causation, so the predicted 17 % → 12 % gain is an upper bound on what a latency fix would
deliver. A staged rollout with instrumentation before the crash would separate the two.

**Statistical note.** With 600 sessions and 101 crashes, the model has adequate power for a
strong effect and little power for the version comparison (which needs thousands of sessions
to resolve a 3 pp difference). Reporting the version *interval* rather than only the p-value
makes that explicit.
